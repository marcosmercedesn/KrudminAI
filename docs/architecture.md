# Architecture

KrudminAI is an isolated Rails engine for authenticated back-office workflows. It uses Propshaft-native assets and module-based Hotwire interactions with Turbo and Stimulus. jQuery is excluded from runtime and test dependencies.

The canonical query pipeline is tenant scope, policy scope, filters, sort, pagination. Every list, search, export, dashboard, and AI context builder must use it. The implemented resource and pipeline contracts are documented in [resource_query_pipeline.md](resource_query_pipeline.md). The mutation pipeline dispatches CRUD, archive lifecycle, and declared resource actions through tenant and action authorization, normalized results, response adapters, field write checks, and required audit hooks. Active Record mutations and audit events share a transaction, so audit failure rolls back the write; see [mutation_pipeline.md](mutation_pipeline.md) and [resource_actions.md](resource_actions.md).

`KrudminAI::ResourceController` owns conventional CRUD delivery for a resource: authentication via configured providers, access-context creation, tenant/policy-scoped query composition, secure record lookup, permitted attributes, create/update/destroy and declared-action dispatch, audit sink resolution, and generic route helpers (`collection_path`, `resource_path`, `new_resource_path`, `edit_resource_path`, and `resource_action_path`). It renders engine-owned default index, new, edit, and show pages when a host has not supplied a matching resource template. A host controller inherits it and declares only `resource OrdersResource`; a host template remains an intentional presentation override. The resource declares its model, route key, tenant key, permitted attributes, labels, list/form/show fields, direct `has_many` relationship metadata, eager-load directives, archive lifecycle metadata, custom actions/transitions, scopes, filters, sorting, and authorization predicates. Nested child IDs are validated through the parent association and child tenant/action predicates before assignment; see [nested_relationships.md](nested_relationships.md). Rails retains one conventional `resources :orders` route registration, including its generic action member route, which the resource generator manages idempotently.

Field read/write decisions deny by default and are enforced before every scalar or nested assignment; read-denied values are omitted while readable/write-denied controls are disabled with accessible explanation text. Generic scalar rendering selects a resource-owned adapter through explicit declarations or safe Active Record schema inference. The adapter owns native form controls, list/detail presentation, JSON, CSV, AI context, parameter normalization, blank handling, and filter metadata. The implemented scalar set is documented in [scalar_field_adapters.md](scalar_field_adapters.md); field-driven filter UI and the remaining sensitive, media, and relationship adapters remain owned by later replacement prompts. The scoped Classic inventory and its durable prompt progress record are maintained in [classic_parity_ledger.json](classic_parity_ledger.json). See [field_authorization.md](field_authorization.md) and [replacement_implementation_prompt_pack.md](replacement_implementation_prompt_pack.md). Five named provider objects (authentication, tenant, authorization, audit, and notification) are validated after Rails initialization. Provider failures deny access or stop the operation; they never silently broaden access. See [provider_contracts.md](provider_contracts.md).

AI context comes only from policy-authorized, tenant-scoped data with approved field allowlists. AI is suggestion-only by default. Mutations require explicit approval and a trace. The implemented assistant contract supports record summaries, record Q and A, document summaries, and report insights; see [ai_assistant.md](ai_assistant.md).

AI provider routing is task-specific and fail-closed: a missing, malformed, or exception-producing provider becomes a safe traced failure rather than an unscoped fallback. Retained traces bind to a tenant and redact output by default; only safe trace metadata is searchable/exportable through the reference store. Durable queued operation lifecycle, trace persistence, and host delivery remain host integration responsibilities; see [ai_assistant.md](ai_assistant.md).

V1.1 AI extraction produces non-persisting, evidence-bearing review drafts. Cross-record and dashboard analysis compose each named source through its own tenant/policy/field-allowlisted context and accept only read-only tools. V2 automation requires an approval policy returning exactly `true`, records actor/roles/tenant/context trace metadata before execution, performs a canonical authorized record lookup, and delegates all writes to `MutationPipeline`; see [ai_assistant.md](ai_assistant.md).

The UI foundation is Hotwire-first: engine-owned CSS tokens, light/dark/system theme selection, inline Lucide SVG icons, and Stimulus controllers support accessible resource tables, filters, form shells, nested editors, status, empty, validation, denial, and pagination states. Generic index, form, and show templates compose stable engine partial components; field and record values remain subject to the same field policies as JSON, AI, and dashboards. `ResourceController` uses an engine-owned admin layout by default, with a persisted desktop navigation rail and a closed-by-default mobile drawer that closes on navigation, backdrop activation, and Escape. Hosts can override the Rails layout conventionally. Hosts register navigation items through configuration with host route helpers, resource-backed label/icon defaults, access-context visibility predicates, and optional active-state predicates that fail closed on non-true or exceptional results. Resources configure an inheritable `icon` identifier for navigation and resource-specific UI. See [ui_foundations.md](ui_foundations.md).

Install, resource, action, dashboard, showcase, and docs-sync generators use idempotent file contracts and managed markers. Generated resources preserve authentication, tenant checks, policy scope, deny-by-default action predicates, and matching Rails integration-test scaffolds. Generated actions live in class-reopening extension files required through their own managed resource marker, avoiding modification of host-authored resource bodies. The showcase has lightweight and full modes; full adds a version-locked, seeded two-tenant conformance scenario for generic CRUD, filters, actions, transitions, audit, and dashboard data. Generated host manifests record enabled modules and provider-binding slots without secrets. Docs sync is restricted to generated documentation and the managed AI instruction block; see [generators.md](generators.md).

Legacy Krudmin migration uses an explicit static audit rather than a lossy automatic rewrite. The audit maps recognized resource constants to KrudminAI concepts, warns where field/search/layout decisions require review, and blocks unsupported generic-editor, state-machine, inline-editing, and bulk-action constructs. The Car/Passenger direct `has_many` recipe and 1.0 release evidence are defined in [migration.md](migration.md) and [release_1_0.md](release_1_0.md).

Dashboards use a host-configurable `Dashboards::Base` widget registry with deny-by-default visibility predicates and normalized loading, empty, error, and ready results. Every widget derives data through the query access pipeline; count and summary widgets use the authorized relation, while table widgets use the complete sorted and paginated path and field-authorized row serialization. Drill-down filters are limited to the target resource's declared filters and must resolve through that resource's controller. See [dashboards.md](dashboards.md).

CSV data operations are explicit resource profiles rather than implicit model serialization. Exports use the same tenant, policy, archive, filter, sort, and field-read rules as other data access, excluding only ordinary index pagination; optional per-field masks are applied before CSV output. Imports have preview and commit phases, require explicit import authorization, validate mapped writable fields, and create each accepted row through the mutation pipeline. Import retry keys require a host-provided durable atomic operation store before a background job/delivery layer is enabled. See [data_operations.md](data_operations.md).

The engine emits redacted structured observability events at request, mutation, audit, and AI boundaries. A request correlation ID joins those events without exposing tenant values, field content, audit records, or AI prompts and outputs. Hosts attach their own logger, metric, and tracing adapters; adapter failure cannot alter protected workflow behavior. Operational alert/recovery, retention, compliance-export, ADR, ownership, release, hotfix, and rollback requirements are defined in [observability.md](observability.md), [governance.md](governance.md), and [the incident runbook](runbooks/incident_response.md).

These architecture contracts do not themselves approve a beta release. The current evidence classification and release outcome are maintained in [the beta readiness checkpoint](beta_readiness_checkpoint.md) and [beta release decision](beta_release_decision.md).
